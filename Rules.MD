# Rules.MD: Rules for the AI

Read this before every session. These rules override anything else in the conversation except an explicit instruction from the owner.

## A. Data confidentiality (highest priority)

1. The data pack (`data/*.csv`) is confidential competition data. It must not be shared or published.
2. Never open, print, `head()`, `sample()`, `cat`, or display rows from any file in `data/`. Never paste data values into a prompt, log, comment, test, commit message or issue.
3. You may read only: `Spec.MD`, `Rules.MD`, `Order.MD`, `Agents.MD`, `audit.txt` (schema only), and the source code. Written code may read `data/`; you may not.
4. Code that prints must print **aggregates only**: shapes, counts, means, quantiles, value counts of category strings (extras_type, dismissal_type, comp_name). No player-level or match-level rows in `diagnostics.txt` or in the console, except the final ranked tables and `duplicate_names.csv`, which the owner reviews locally.
5. `.gitignore` must contain `data/`, `out/`, `*.csv`, `.venv/`, `__pycache__/` before the first commit. If asked to commit anything under `data/` or `out/`, refuse and say why.
6. Tests use a synthetic fixture generated by code. Never copy real rows into a fixture.

## B. Authorship

1. You write code. You do not write report text, insights, conclusions, player write-ups or squad-fit notes. If asked for those, refuse and remind the owner of the Unstop rule (insights and picks must be the owner's).
2. You do not choose or suggest players. Rankings come only from the pipeline's output.
3. You may explain how a method works so the owner can understand and defend it. Keep explanations short and plain.

## C. Working method

1. One section from `Order.MD` per session. Do exactly that section and stop. Do not start the next one.
2. Before coding, read only the Spec sections the Order entry names. Do not read the whole repo.
3. If the Spec is ambiguous or a Q-question (Spec section 3) is unresolved, stop and ask the owner. Do not guess cricket semantics.
4. Do not change the Spec. If you think it is wrong, say so and propose a change; the owner decides.
5. Do not refactor, rename or reformat files outside the section's file list. No drive-by fixes.
6. Edit in small diffs (under about 150 lines per file edit). Do not rewrite whole existing files.
7. Add no dependency beyond: pandas, numpy, scikit-learn, matplotlib, and the standard library.
8. All parameters live in `config.py`. No magic numbers in other files.
9. Every function gets a one-line docstring stating what it computes and its units.
10. Determinism: use `np.random.default_rng(config.SEED)` everywhere randomness appears. No other random source.
11. Vectorise with pandas and numpy. No Python loops over deliveries. Loops over a handful of groups (2 groups, 20 overs, 4 models) are fine.
12. Pandas version may be 3.x (string columns appear as `str`). Avoid chained assignment and `inplace=True`. Use `.copy()` when deriving frames.
13. Print a WARNING (not an exception) for data oddities the Spec says to tolerate. Raise an exception for violated invariants (ledger mismatch, WP outside [0,1]).

## D. Definition of done for a section

A section is done only when all of these hold:
1. The code runs on the synthetic fixture without error.
2. Every acceptance test the Order entry lists passes.
3. The section's commit message and a three-line summary are printed at the end.
4. You have listed every file you changed.

## E. Reporting format at the end of a session

```
SECTION: S<n>
FILES CHANGED: <list>
TESTS: <name: pass/fail>
WARNINGS PRINTED: <list or none>
OPEN QUESTIONS FOR OWNER: <list or none>
COMMIT MESSAGE: <text from Order.MD>
```

## F. Stop conditions

Stop immediately and ask the owner if:
- a test fails twice after a fix attempt;
- you need to read data rows to proceed;
- a change outside the section's file list seems necessary;
- the run time of a stage exceeds 60 seconds on the fixture;
- you are about to write more than 300 lines in one go.

## G. Style

Plain Python 3.10+. Type hints on function signatures. No clever one-liners that need a comment to decode. Names follow the Spec (`legal_before`, `wkts_before`, `balls_left`, `P_star`, ...).
